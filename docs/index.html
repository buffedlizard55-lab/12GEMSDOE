Why Group Submissions Repeatedly Scored 0.1563

Our line-by-line byte hash and pixel array comparison resolved the 0.1563 mystery:

  • GEMSDOE1 and 5GEMSDOE were Byte-for-Byte Identical: Both published TIFF files have the exact same SHA-256 (7f00890a62878d612fb5eef67a9a364a2df819433dde74b6762ce4fc0fc4fe15) and size (570,890 bytes). 5GEMSDOE re-uploaded GEMSDOE1's ens12 file under account SDCF9. Because the submission files were identical, DrivenData assigned them the identical score of 0.1563.
  • 8GEMSDOE Anchored to the Same 0.1563 File + Masked Labels: 8GEMSDOE's build_hedge_v2.py combined the 7f00890a base with known USGS fault labels (labels.tif). However, DrivenData Staff confirmed: "Pixels corresponding to known USGS/INGENIOUS faults are masked / excluded from evaluation, so they do not count towards penalty terms." Adding known faults to the 0.1563 file had zero effect on the hidden test set, producing the identical score of 0.1563.
  • Low Scores (0.0107 to 0.0343) in Other Repos: Caused by uncalibrated high area budgets (e.g. 6% binary mask = 310,000 pixels of 1.0) which triggered catastrophic false positive penalties on the sparse hidden test set.
