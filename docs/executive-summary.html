Troubleshooting: The "Predicted values must be in range [0, 1]" Error

What the Error Does — and Does Not — Establish

The rejected file and DrivenData's parser log were not retained, so the message alone does not prove a single cause. Two sufficient causes are now verified locally, and they are checked in this order:

  1. The training_features.tif missing-data sentinel (verified, most likely cause of a real rejection). The supplied feature stack does not use NaN for missing data — it uses the float32 most-negative sentinel -3.4028235e+38, and it is suppressed only by rasterio's masked read. Measured this session (evidence/round5-identity-checks.json, check C1): an unmasked read of the stack has minimum -3.4028235e+38, and band tc alone carries 3,073 sentinel pixels inside the survey footprint. Any pipeline that reads the stack without masked=True puts -3.4e+38 into the model inputs and then into the output raster — which fails a [0, 1] range check exactly as reported. Fix: always src.read(i, masked=True).filled(np.nan), impute, and re-assert the range before writing. Our own writer (core.write_prediction) refuses out-of-range values instead of clipping them.
  2. A range check run on an unmasked read of a NaN-containing raster (verified behaviour, unproven cause). The official sample_submission.tif is itself NaN outside the footprint (verified: 7,111,787 NaN pixels, nodata = NaN). With a masked read, np.all((a >= 0) & (a <= 1)) is True for our file; with an unmasked read of the same file it is False, because NaN fails both comparisons. Since DrivenData's own sample must pass its own checker, the masked reading is the likely one — but the primary/fallback pair below makes the distinction testable in one attempt instead of guesswork.

Local checks that must pass before any upload (all automated in scripts/core.py:validate() and scripts/generate_nms_submission.py): grid equality with the template (CRS, transform, width, height); exactly one band; float32; every footprint pixel finite and in [0, 1]; NaN outside the footprint; and a .zip containing exactly one GeoTIFF.

Protocol if it happens again: upload the primary .tif; if the form returns the range error, upload the all-finite fallback once and record which file was rejected. The two differ only outside the survey footprint (NaN vs 0.0), so the answer identifies which check DrivenData runs — knowledge worth more than the slot.

H32 = 12 label-free channels per 100 m cell from the USGS 3DEP 1/3 arc-second (~10 m) DEM (public domain; built on a GitHub runner by sibling GEMSDOE10, tag ext/dem10-36343078537; every tile and channel re-hashed here — dem10-fetch.json). Distinctness was reported honestly: slope-type channels correlate 0.80–0.97 with the supplied det_elev_slope; the one-sided scarp-asymmetry channels are the new information and alone still win 4/4. Artifact 12GEMSDOE_r7-nms3-dem10-scarp_0c9199f14e62.tif; no slot spent. Evidence: holdout_round7.json · round7-feature-build.json · knowledge base.

What Changed in Round 6 (and Why H28 Matters)

Round-6 preregistered five mechanism-distinct hypotheses H25–H29 before coding. All below 0.50 max |corr| vs rounds 1–5: H25 0.4301, H26 0.336, H27 0.339, H28 0.384, H29 0.120. Frozen masked holdout, NMS-3 @2%, both truth protocols, leakage probe 0.0000 every fold. H28 magnetic texture variance (mag_anom local std 11 px) is the only arm to beat multi25+NMS on ≥3/4 folds on BOTH protocols — dense 3/4 (0.22143 vs 0.22138), sparse 3/4 (0.11438 vs 0.11178, +0.0026). H25 passes sparse 3/4 but dense 1/4; others fail. New artifact 12GEMSDOE_r6-nms3-h28-texture_8721329b55c7.tif packaged; no DrivenData slot spent. Evidence: holdout_round6.json · feature-build.json.

Why H28 should catch missing faults: Hydrothermal alteration destroys magnetite along fault damage zones, creating disrupted magnetic texture (high local variance) rather than clean edge. USGS QFFD requires surface geomorphic scarps; subsurface alteration halo beneath non-magnetic alluvium is invisible to surface mapping but visible to magnetics. H28 uses mag_anom (B1) local standard deviation in 11 px window, distinct from all prior transforms (max |corr| 0.384 vs tmi_hg). Layers: B1 only. Physical signature: texture disruption, not edge.

What Changed in Round 5 (and Why It Matters More Than Any Feature)

Before changing anything, the frozen holdout was re-run from scratch and reproduced the committed numbers bit-exactly: raw19 0.08602428869798472 · multi25 0.09071277311870418 · multi30 0.08888636948563039 · random02 0.1378794777374697, matching evidence/holdout_masked.json on every fold of every arm (the reproduction report is written to the git-ignored data/cache/ tree by scripts/cache_fold_models.py; the full table is in the Round-5 register and session-review §10).

That reproduction exposed the defect: uniform random 2 % emission scores 0.13788 on this protocol — better than every learned arm built in four rounds. The metric credits a truth pixel if any prediction lands within 300 m (3 px) and takes the max over that 5 × 5 cell, so extra predictions inside one cell add false-positive mass and no credit. Fixing only the emission geometry — 5 × 5 non-maximum suppression instead of top-k — with the identical model and features gives:

  • dense truth 0.09071 → 0.22138 (2.44×)
  • sparse truth (20 % of truth components) 0.04489 → 0.11178 (2.49×)
  • off-catalogue candidates only, the strictest local analogue of real scoring, 0.06759 → 0.19380 (2.87×, 4/4 folds)

Round-5's four new geological channels (H20–H23) did not clear their gate once the emission was fixed — all arms now sit within ±0.0008 (dense) and ±0.0018 (sparse) of each other. Recorded as a negative result, not buried.
